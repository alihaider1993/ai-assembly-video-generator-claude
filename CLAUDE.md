# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Python pipeline that turns any furniture assembly manual (PDF) into an animated assembly video. It runs **fully offline and free**. No vision model reads the pages. Instead, Claude Code reads a new manual's page images and writes `manuals/<name>/describe.py`, a page-by-page description of the parts, fasteners, actions and sizes (the `/describe-manual` skill). From that the pipeline builds an assembly graph and motion plan, generates a Blender script, renders frames headlessly in Blender, and stitches them into an MP4 with step captions. A Streamlit UI (`app.py`) adds manuals and runs the pipeline.

There are no Azure, Ollama or other model calls anywhere, and none should be added: the user chose this. Keep the code general. Nothing should be special-cased for one manual.

## Commands

All scripts assume the **repo root is the working directory**, because most stages use relative paths like `Path("v2/outputs/json/...")`.

```bash
.venv\Scripts\activate                 # Windows venv
pip install -r requirements.txt        # direct dependencies only

python utils/pdf_to_images.py <pdf> [name]   # add a manual: manuals/<name>/manual.pdf + pages/page_<n>.png
python manuals/<name>/describe.py            # (re)generate its page_states.json + diagram_analysis.json
python v2/run_mvp_pipeline.py <name>         # build the video → outputs/videos/<name>.mp4
python v2/run_mvp_pipeline.py <name> --quiet # same, without per-frame lines (full log: outputs/logs/pipeline.log)
python v2/run_mvp_pipeline.py <name> --no-render # stages up to the Blender script only (no Blender, no video; what CI runs)
python utils/page_sheets.py <name> [--page N --split 2]  # page images sized for reading (manuals/<name>/sheets/)
python utils/layout_summary.py               # last run's layout + motion plan as a short table
python utils/sample_frames.py <name> [--at S] # grid of video frames → outputs/checks/
python utils/layout_regress.py check [NAME ...]  # re-run manuals (no render) and compare layouts with v2/tests/layout_snapshots/
python utils/layout_regress.py update NAME ...   # after an intended layout change: save new snapshots and commit them
python utils/review_sheet.py [NAME ...]          # every manual's finished piece on one image (last frame only, ~6 s each) → outputs/checks/review_sheet.png
streamlit run app.py                         # UI: add a manual, pick one, generate, play/download
python web/worker.py                         # this PC as the render machine: uploads on the live site open while it runs
cd deploy/cloudflare && npx wrangler deploy  # publish the website (Cloudflare free plan; builds public/ from web/static + showcase)
uvicorn web.server:app --port 7860           # the website self-hosted (site + uploads in one server; what the Dockerfile runs)
python utils/showcase.py add NAME [NAME ...]  # put a finished video on the website (showcase/<name>/, committed)

python <any stage script>              # each stage is standalone; rerun one to iterate on it

pytest v2/tests                                                     # validates generated JSON, so run the pipeline first
pytest v2/tests/test_mvp_visual_pipeline.py::test_shape_types_are_valid  # single test
```

Environment (`.env`, optional): `BLENDER_EXE`, defaulting to `C:\Program Files\Blender Foundation\Blender 5.1\blender.exe`.

## Keeping token use down

Use the tools above instead of reading raw output: run the pipeline with `--quiet`, check layouts with `layout_summary.py`, and read pages and frames through `page_sheets.py` / `sample_frames.py`, which size images to what the model can use. Don't trade away detail: read small print with `--page N --split 2`, and open the full JSON or log when a summary shows a problem. Use Grep rather than reading the large stage scripts (`scene_layout_engine.py`, `blender_builder_v3.py`) whole.

## Manuals

Each manual is a folder `manuals/<name>/`:
- `manual.pdf` and `pages/`: git-ignored.
- `describe.py`: written by reading the pages.
- `page_states.json` and `diagram_analysis.json`: generated by `describe.py`, and the pipeline's input.
- `product.json`: the product title (`write_description(..., title=...)`), shown at the top of the video; `config.product_title()` falls back to the folder name.

`config.is_described()` tells whether a folder has both JSON files. To describe a new manual, follow `.claude/skills/describe-manual/SKILL.md`. It covers the procedure, the part-name words the layout understands, and the quantity, "Repeat xN" and size rules. Edit `describe.py` and re-run it rather than hand-editing the JSON.

The examples in the repo:
- `melltorp_table`: IKEA MELLTORP
- `banbury_chair`: Habitat Banbury, one chair of the pair
- `kaycie_bed`: Habitat Kaycie
- `new_table_manual`: IKEA NORDEN extendable table, which prints no sizes

`describe.py` files use the helpers in `v2/agents/manual_description.py`. `part()` also takes an estimated `size=(w, d, h)` in mm (for manuals that print none), a lean `tilt=` in degrees and a traced `profile=` outline. The extractor reads these from `page_states.json` by part name, and the Gemini describer (`v2/agents/gemini_describer.py`, used for unattended uploads) asks for the same fields. Those pass every page through `v2/agents/vision_schema.py` (`validate_page_state`, `validate_diagram_analysis`), which fills defaults and assigns stable uids (`P007_003`, `F005_001`, `D004_002`).

## Architecture

**All pipeline code is in `v2/`.** From the root it only uses `config.py` (and `utils/pdf_to_images.py`, which adds manuals).

**The pipeline is a chain of standalone scripts connected by JSON files on disk.** It is not an in-process call graph. `build_steps()` in `v2/run_mvp_pipeline.py` holds the order and runs each stage as a subprocess (copies run in-process as `CopyStep`). Central paths live in `config.py`, but many stages hardcode their own `Path("v2/outputs/json/...")` constants. If you rename or move an artifact, grep for every reader.

Stage order (outputs go to `v2/outputs/json/` unless noted):
1. Copy the manual's `page_states.json`.
2. `state_difference_engine.py` → `assembly_deltas.json`; `assembly_action_extractor.py` → `assembly_actions.json`. The extractor infers part-to-part links from evidence text when a page reports only fastener actions, but never for `insert` actions (dowels into a part).
3. `universal_graph_engine.py`, **pass 1** → `universal_assembly_graph.json`
4. `object_identity_tracker.py` → `object_identity_map.json`; `canonical_resolver.py` → `resolved_assembly_actions.json`
5. `action_replicator.py`: expands actions across sibling instances (e.g. 4 rails, 2 legs). It overwrites `resolved_assembly_actions.json` in place. When the action's page shows several copies (`quantity_visible` > 1) or the evidence says "Repeat xN", replicas are capped at that count; a single drawn copy still expands to the whole group.
6. `universal_graph_engine.py`, **pass 2**. The graph engine prefers `resolved_assembly_actions.json` and the identity map when they exist, so the second run picks up the replicated actions. That is why it runs twice.
7. `motion_planner.py` → `motion_plan.json` (each node moves in exactly one step); `geometry_synthesizer.py` → `geometry_spec.json`
8. Copy the manual's `diagram_analysis.json`, then mirror it into `v2/output/`.
9. `part_shape_extractor_agent.py` → `v2/output/part_shapes.json`. Despite the name it makes no model call. It gives each part a `role` from its name (`PART_ROLES`: tables and chairs, beds, cabinet carcasses (side/back/front panels, dividers, shelves, lids, plinths), doors, drawer parts, handles, hinges, and upholstered bodies and cushions) and sizes it from the measurements (defaults by role when the manual prints none). The leg_frame, back and side_frame roles get the composite primitives `u_frame` / `slatted_back` / `side_frame`. Then `scene_layout_engine.py` → `scene_layout.json` (mirrored into `v2/output/`), using the one layout in `general_layout.py` for every product. It treats the piece as a box frame: each part is an upright, wall, beam, plate or block (`part_kind`: from its role, else its proportions). Walls and uprights stand on the floor, beams run along the frame's edges or across it and are stretched to fill the gap between the parts at their ends, plates rest on what they are joined to (or span between two side walls, like shelves), and brackets go into inside corners. In a carcass, legs or feet raise it, shelves are spread up each compartment between the sides and dividers, and doors and drawers (each with its sides, back, bottom and runners) fill the front opening, with handles and hinges on them. Upholstered bodies (a sofa section, a chaise) stand side by side on their feet, with cushions on top and the joining hardware in the joint. The assembly graph decides which edge and height a part goes to, and name words (front/back/head/foot, left/right, side/long, end/short, cross, top, bottom) only break ties. Measured sizes set the frame's size before role defaults do. A piece whose base part (never moved, the target of the most steps) ends up in the top half is laid out upside down and turned over by a `finale` flip. There is one fastener instance per (fastener, host part) pair (`FAST0001_1`, ...). Parts the frame can't place, such as those with no joins, get the older ring layout. Improve `general_layout.py` for a new kind of product rather than adding a layout for one product. `scene_layout_engine.stage_subassemblies` then finds sub-assemblies: a part that others are fitted to before its own step (a chaise getting its feet before it joins the sofa) is built at a staging spot beside its place and moves there with everything on it. These nest, and are written to the layout as `own_end`, `carry` and `reveal_with`. Then `builders/proxy_geometry_builder.py` → `v2/output/proxy_geometry.json`.
10. `blender_builder_v3.py` **generates** a Blender Python script (an f-string template) at `blender/generated/v3_generated_blender_scene.py`. Blender runs it with `--background` and renders PNGs into `outputs/frames_v3/`. Parts with a traced outline (`profile`) are drawn as extruded strips or filled shapes (`create_profile`), so bentwood frames, curved slats and an upholstered body's side come out the right shape. Captions take fastener counts from the manual's "4x" in the action's evidence. The camera orbit ends at the front. The timeline merges consecutive steps that do the same thing to the same kind of part. Fasteners are drawn enlarged (`MIN_FASTENER_SIZE`) while they move, then shrink to real size. Fasteners that no step moves are not drawn.
11. `render_video.py` (moviepy) → `outputs/assembly_animation_v3.mp4` with the step captions burned in and the product title (`--title`) centred at the top; the Blender camera keeps that band (`TITLE_BAND`) clear of the furniture. `run_mvp_pipeline.py` then keeps a copy as `outputs/videos/<name>.mp4`.

Key points:
- There are two output directories, `v2/outputs/json/` (graph/motion stages) and `v2/output/` (shape/proxy-geometry stages). Tests read `v2/output/`.
- `blender_builder_v3.py` runs under normal Python. Code inside its template string runs inside Blender (`bpy`, `mathutils`), so it can't import project modules unless it adds the project root to `sys.path`. Escape literal braces as `{{ }}` in the template.
- `app.py` follows progress by matching stage script names in the runner's `RUNNING: ...` lines (`detect_step`). Renaming a stage script can break the progress display.
- Generated outputs (`outputs/`, `blender/generated/`, `v2/outputs/json/*.json`, `v2/output/*.json`), `uploads/` (a drop folder) and each manual's PDF and `pages/` are git-ignored.
- Output paths are fixed. Run manuals one at a time, or copy the repo into a separate sandbox for each run.
- The full run is Windows-first because of the default `BLENDER_EXE` path.
- The live website runs on Cloudflare's free plan (`deploy/cloudflare/`: static site, upload API, and a Durable Object holding jobs, PDFs and videos). This PC renders: `web/worker.py` polls it for uploads and runs them with `web/pipeline_job.py`, which `web/server.py` shares. Uploads are open only while the worker runs.
- The public website (`web/`) must not expose the pipeline: browsers get only `showcase/` files (titles, captions, page numbers, part names) and a job's state, a plain-language phase and a generic error. No stage names, ids, logs, JSON or API docs.
- CI (`.github/workflows/ci.yml`, GitHub Actions on Ubuntu) runs every described manual with `--no-render`, checks its layout against its snapshot (`utils/layout_regress.py`), compiles the generated Blender script, runs `pytest v2/tests`, and runs `pytest mcp_server/tests`. Add a new manual to its matrix and save its snapshot (`layout_regress.py update NAME`). Before committing a layout change, run `layout_regress.py check` on all manuals: a part that moves in another manual is a side effect to look at.
